# C.3 reviewed clinical record foundation — implementation notes

**Status: accepted C.3 technical checkpoint (11 October 2026).**

The live acceptance gate processed one synthetic CT report through the actual MRJ HTTP application and Accept & Save. Reviewed record `f30c97e7f37d557dba6805b2a61afbb0` was read before restart, Uvicorn was fully stopped and port 8001 closed, and a new canonical Uvicorn process recovered the same accepted record without re-upload or reprocessing. The former in-memory Journey returned 404; the durable record API returned 200 with two clinical facts, protected evidence, a verified source digest and exact anchor, current version 1, and version-1 history. The original synthetic upload bytes, identifier markers, and filename were absent from the reviewed-record persistence payload. This is an integration and durability proof, not clinical validation.

The live `JourneyStore` still owns transient processing state. On acceptance, it builds an MRJ-owned `ReviewedClinicalRecord` from the current PROTECT, EXTRACT, and STANDARDIZE outputs. It first commits that record through `ReviewedClinicalRecordRepository`, then mirrors `REVIEWED`, the timestamp, and the stable record ID into Journey. A failed write leaves the Journey report unreviewed and the HTTP endpoint returns a generic retryable error. The repository, not the Journey or batch metadata file, is the authority for `durably_reviewed` and future Collection admission.

The V1 JSON envelope has an explicit `schema_version`, stable UUID5 logical ID derived from Journey run and document IDs, immutable integer `record_version`, acceptance timestamp and decision, Major Review issue/acknowledgement, protected canonical text and SHA-256, protected artifact reference and available policy metadata, safe categorical exam context, accepted summary and canonical facts, exact validated evidence anchors, observations/attributes/measurements, fact-linked standardization metadata, and limited stage provenance. It deliberately excludes upload bytes, original identified text, original filename, original exam name, transient `DocumentContent`, raw engine candidates/debug diagnostics, full stage responses, and generated protected PDF bytes. A protected PDF digest is retained when available. The protected canonical text is the evidence artifact that can be reconstructed after restart; offsets, quote, and artifact digest are checked before exact highlighting. Any failed check must result in unhighlighted protected context.

The SQLite implementation uses `schema_migrations` (schema 1), append-only `reviewed_record_versions` with an envelope SHA-256, and `reviewed_record_heads` with a foreign key to the current version. `save` uses a transaction, parameterized SQL, foreign keys, `synchronous=FULL`, and an instance lock. Repeated saves of identical version content are idempotent; conflicting content at the same version is rejected. Version 2 can be appended later without replacing version 1. The JSON contract is deterministically serialized and validated independently of SQLite, so a future repository adapter can implement the MRJ protocol without changing clinical processing or importing another platform's classes.

The default database is `%LOCALAPPDATA%\MRJ\reviewed_records.sqlite3` on Windows and `${XDG_DATA_HOME:-~/.local/share}/MRJ/reviewed_records.sqlite3` elsewhere. `MRJ_REVIEWED_RECORD_DB` overrides the full file path. Tests use isolated temporary databases. The database is outside the source repository by default; operators should also keep any configured path outside Git. A logical ID uses opaque run/document IDs, never a report filename. The current API adds `GET /api/v1/understanding/reviewed-records`, `GET /api/v1/understanding/reviewed-records/{id}` (optional `version`), `GET /api/v1/understanding/reviewed-records/{id}/versions`, and `GET /api/v1/understanding/journey-runs/{run_id}/documents/{document_id}/reviewed-record`. Responses are private/no-store. `POST .../accept` accepts optional `major_review_acknowledged`; the accepted UI sends it only after the explicit Major Review confirmation.

The database contains **plaintext protected clinical content**. This phase does not add encryption at rest, record-level authorization, backup encryption, deletion/retention policy, or audit logging. Access currently relies on the local OS account, filesystem permissions, and the application's existing API perimeter; desktop deployment must harden these before real clinical use. Backups and filesystem snapshots include protected clinical data and need the same controls. SQLite errors are hidden from the clinician-facing acceptance response, and the new code does not log record envelopes or report text. The explicit original-report comparison path remains separate. Existing batch metadata and Collection Analysis persistence are unchanged; Collections must later consume only repository IDs/versions whose durable accepted record exists.
